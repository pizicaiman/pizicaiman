# 可观测性与告警治理 · 面经

## 核心问题
1. 指标、日志、链路三者是什么关系？在排障时如何配合使用？
2. Prometheus 的架构和工作原理是什么？为什么适合云原生场景？
3. 告警太多怎么治？怎么做告警收敛和分级？

## 答题要点
- **三支柱（Three Pillars）各有侧重**：
  - 指标（Metrics）：时序数值数据，回答"系统怎么样"，聚合成本低、查询快，适合监控告警。代表：Prometheus + Grafana。
  - 日志（Logs）：离散事件流，回答"发生了什么"，细节最全但量大难查。代表：Loki、ELK。
  - 链路（Traces）：请求在分布式系统中的调用链，回答"在哪慢、在哪错"，跨服务追踪。代表：Jaeger、Tempo、SkyWalking。
  - 三者通过 label（指标标签）、traceId（链路 ID）、服务名关联，构成排障闭环：告警触发 -> 看指标定位异常 -> 查链路定位慢点 -> 查日志定位根因。
- **Prometheus 架构**：
  - Pull 模型：Prometheus 主动抓取 exporter（HTTP /metrics 端点），不用 Push（避免被动积压）。
  - 多维 label：每个样本带标签，支持 PromQL 灵活聚合。
  - 本地 TSDB + 远端存储（Thanos/VictoriaMetrics/Mimir）解决长期存储与高可用。
  - 服务发现：支持 K8s、Consul、文件等动态发现抓取目标，云原生友好。
  - Alertmanager：告警路由、分组、抑制、静默。
- **告警收敛四大手段**：
  - 分组（Grouping）：按 alertname + 应用 + 集群聚合，相同告警合并成一条通知。
  - 抑制（Inhibition）：高优先级告警触发时自动屏蔽相关低优先级告警（如节点挂了抑制该节点上的 Pod 告警）。
  - 静默（Silence）：计划内变更、维护期间临时屏蔽。
  - 分级（P0-P3）：按影响面与紧急程度分级，P0 电话/短信、P1 IM、P2 工单、P3 日志，避免"所有告警一样响"。
- **黄金信号（Google SRE）**：延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）。配合 USE 方法（资源：Utilization/Saturation/Errors）和 RED 方法（服务：Rate/Errors/Duration）设计指标。
- **告警设计原则**：可执行（收到能动手）、有意义（面向用户感知而非底层指标）、收敛（同类合并）、分级（响应时效不同）。从"指标告警"升级到"SLO/SLI 告警"，基于错误预算燃烧率告警更贴近用户体验。

## 加分回答
可观测性的本质不是"装一堆监控"，而是"在故障发生前能看见，在故障发生后能定位"。很多团队的监控很全但仍然排障慢，根因是"三支柱各自为政"--指标告警了找不到对应链路，链路找到了对应日志要靠时间戳猜。成熟做法是用 traceId 贯穿三支柱：指标按 traceId 采样、日志按 traceId 关联、链路按 traceId 串联，告警触发时直接给出 traceId 链接，一键跳转到链路与日志。服务网格（Istio）能自动注入链路埋点与指标，减少应用侵入，是云原生可观测性的重要基础设施。

告警治理是"组织问题"而非"技术问题"。技术上 Alertmanager 的分组/抑制/静默都好实现，难的是"告警价值观"的对齐--什么该告、告给谁、多久响应。建议建立"告警 SLI"：告警准确率（真正需要响应的比例）、告警召回率（真实故障被告警覆盖的比例）、MTTA（平均响应时长）、MTTR（平均恢复时长），定期复盘"无效告警"与"漏告警"，持续迭代告警规则。一个反直觉的结论：告警数量应该随系统稳定而下降，如果告警一直很多，说明收敛没做到位，要么是规则太敏感，要么是根因没修。

## 口播版短文案
可观测性三支柱，指标、日志、链路，各管一摊。指标回答系统怎么样，日志回答发生了什么，链路回答在哪慢在哪错。三者通过 traceId 串起来，告警一响，看指标定位异常，查链路定位慢点，查日志定位根因，闭环。Prometheus 为啥适合云原生，就一个词：Pull。它主动抓 exporter，配合 K8s 服务发现，Pod 一扩缩自动感知，不用改配置。告警太多怎么治，四招：分组把同类合并，抑制让高优屏蔽低优，静默在维护时临时关，分级让 P0 电话 P3 工单别一样响。记住一句话：告警应该面向用户体验，不是面向底层指标，从指标告警升级到 SLO 告警才是正道。
