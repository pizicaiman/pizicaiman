# CI/CD 与 GitOps · 面经

## 核心问题
1. 一条规范的 CI/CD 流水线应该包含哪些阶段？每个阶段的关键产出是什么？
2. GitOps 和传统 CI/CD 有什么区别？优势在哪？什么场景适合用？
3. 灰度发布有哪些方式？回滚怎么做才能又快又安全？

## 答题要点
- **CI 阶段（持续集成）**：代码检出 -> 依赖安装 -> 单元测试 -> 静态扫描（SonarQube/golangci-lint）-> 构建产物 -> 镜像构建（多阶段 Dockerfile）-> 镜像扫描（Trivy）-> 推送仓库。关键产出：经过验证的可部署镜像 + 测试报告。
- **CD 阶段（持续部署/交付）**：环境配置注入 -> 部署到目标环境 -> 冒烟测试 -> 健康检查 -> 流量切换 -> 监控观察。关键产出：可运行的生产服务 + 变更记录。
- **GitOps 核心思想**：Git 仓库作为部署状态的"唯一事实源"（Single Source of Truth），声明式描述期望状态（YAML/Kustomize/Helm），ArgoCD/Flux 在集群内 watch Git 仓库，发现差异自动同步。
- **GitOps vs 传统 CI/CD**：
  - 传统：CI 工具（Jenkins）直接 kubectl apply 推送到集群，凭证下发到 CI，Push 模型。
  - GitOps：集群内 Agent 主动拉取 Git 期望状态，Pull 模型，集群不需要暴露给 CI，凭证收敛。
  - 优势：变更可审计（git log）、可回滚（git revert）、环境一致（同一套 manifest）、权限收敛（CI 不直连集群）、多环境差异通过 overlay 管理。
- **灰度发布方式**：
  - 滚动更新（RollingUpdate）：逐批替换，K8s 原生支持，简单但流量比例不可控。
  - 蓝绿发布：两套环境（蓝/绿）切换流量，瞬时切流，资源翻倍但回滚快。
  - 金丝雀（Canary）：按比例小流量验证再放量，配合 Istio/APISIX 做细粒度路由。
  - A/B 测试：按用户特征路由（如 header、user_id），用于业务效果对比。
- **回滚策略**：
  - 滚动回滚：`kubectl rollout undo`，回到上一 ReplicaSet。
  - GitOps 回滚：`git revert` 回退 manifest commit，ArgoCD 自动同步。
  - 镜像 tag 复用：生产镜像 tag 不覆盖，回滚切回历史 tag 即可（不要用 latest）。

## 加分回答
GitOps 不只是工具升级，更是部署范式的转变。传统 CI/CD 把"部署"看作一次动作，GitOps 把"部署"看作一个持续协调的状态--集群实际状态偏离 Git 期望状态时自动纠正（auto-heal）。这带来三个深层收益：一是"谁改了集群"有了单一答案（必须改 Git），杜绝了登录节点 kubectl 改配置的"野操作"；二是回滚从"找上次部署脚本"变成"git revert 一下"，确定性大幅提升；三是多集群场景下，同一份 manifest 可同步到多个集群，环境漂移问题自然消失。但 GitOps 也有代价： secrets 管理（不能明文进 Git，需 Sealed Secrets/SOPS/External Secrets）、变更频率受 Git 提交节奏约束、对"非声明式资源"（如手工创建的 ConfigMap）的治理需要纪律。

灰度发布的难点不在"切流量"，而在"判断能不能继续放量"。成熟的做法是：金丝雀阶段接好监控（错误率、RT、业务指标），设定自动判断规则（如错误率 > 0.5% 自动回滚），避免人工盯盘。更进阶的是接入 Service Mesh（Istio）做按 header/user_id 的精准路由，让内部用户先验证再放量给外部用户。回滚要警惕"数据兼容性"陷阱：如果这次发版带了数据库 schema 变更（如加字段、改类型），直接回滚老代码可能因 schema 不兼容而启动失败。生产纪律是"schema 变更必须可前可后"（先兼容性变更，再分多次发版演进），避免不可逆变更锁死回滚路径。

## 口播版短文案
面试问 CI/CD 怎么设计，别光说构建部署，给你一套完整链路。CI 阶段：拉代码、跑单测、静态扫描、构建镜像、镜像扫描、推仓库，产出是一个经过验证的镜像。CD 阶段：配环境、部署、冒烟、健康检查、切流量。再讲 GitOps，这是这两年的趋势，一句话：Git 仓库是唯一事实源，ArgoCD 在集群里盯着 Git，发现不一致自动同步。好处是变更可审计、回滚就是 git revert、CI 不用直连集群凭证收敛。灰度发布四种：滚动、蓝绿、金丝雀、A/B，生产推荐金丝雀配 Istio 做细粒度路由。最后回滚有个大坑，数据库 schema 变更要可前可后，不然回滚老代码直接起不来，这点踩过的人都懂。
